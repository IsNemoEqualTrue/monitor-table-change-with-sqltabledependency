# AGENTS

## Project overview
- SqlTableDependency library for SQL Server table change notifications.
- Fork of `https://github.com/IsNemoEqualTrue/monitor-table-change-with-sqltabledependency` but on .NET and async support.
- Main library: `TableDependency.SqlClient/` (net10.0).
- Unit tests: `TableDependency.SqlClient.Test/` (xUnit v3, Testcontainers MsSql).
- Other manual tests live under `TableDependency.SqlClient.Test.*` projects (Aspire AppHost, client, load tests, crash sim), see `RunningTests.md` for local SQL Server details.
- IDE solution file: `TableDependency.slnx`.

## Build
- `dotnet build TableDependency.SqlClient/TableDependency.SqlClient.csproj`

## Tests
- `dotnet test TableDependency.SqlClient.Test/TableDependency.SqlClient.Test.csproj`
- You can run tests, as the SQL Server is started by testcontainers when running `dotnet test` automatically.
- Don't run all tests at once as they take over 20 minutes, just ones added or updated.

- If you add/remove projects, update the `.slnx`
- The `WaitForNotificationsAsync` loop must arm `BEGIN CONVERSATION TIMER` in persisted mode too: it is the only thing that retires an idle initiator dialog. The `DialogTimer` fires onto the `_Sender` queue, whose activation procedure runs `END CONVERSATION` (its drop-all script is empty when persisted, so objects survive). Drop it and persisted dialogs stay `CONVERSING` forever — any test that waits for a persisted conversation to self-close (e.g. `Pr232`) hangs.
- On container stop (Kubernetes rollout = SIGTERM) the long-running `WAITFOR` connection is severed. The resulting `SqlException` can be thrown *before* the `StartAsync` cancellation token has propagated, so checking only `ct.IsCancellationRequested` in the `WaitForNotificationsAsync` catch loses the race and reports a benign shutdown as `StopDueToError` + `OnException`. The fix latches `_shuttingDown` from a `PosixSignalRegistration` on SIGTERM/SIGINT/SIGQUIT; the signal precedes both the token cancel and the socket teardown, so the catch can treat the drop as a clean stop. A genuine mid-operation outage (no signal) still surfaces via `OnException`. The shutdown fast path is keyed off the listener's own connection: it is benign only when `sqlConnection.State is Closed or Broken` (the severed receive pipe). A subscriber/mapper fault — even one that is itself a `SqlException` — leaves that connection usable (`State` is not `Closed`/`Broken`; while a reader is open it carries `Fetching`/`Executing`, so do NOT test `!= Open`), so it still surfaces as a real error. `sqlConnection` is therefore hoisted above the `try` and disposed in the `finally` so the catch can read its state before disposal. Arm the registration in `StartAsync` and dispose it in `StopAsync`, NOT the ctor/`DisposeAsync`: the handler delegate captures `this`, and `PosixSignalRegistration` holds it in process-wide static state, so a ctor registration roots the instance until `DisposeAsync`. `TestCollapsingIsolatedContext` only calls `StopAsync` and then asserts its collectible `AssemblyLoadContext` unloads — a registration that outlives `StopAsync` pins the ALC and the test fails with "failed to unload after disposal". Dispose the registrations in a `finally` in `StopAsync` so a faulting worker task can't leave them pinning the instance. The latch is never auto-cleared by the runtime, so `StartAsync` resets `_shuttingDown = false` before re-arming — otherwise an intercepted SIGINT that the host survives would leave the latch set and a genuine outage on the *next* `StartAsync` would be silently swallowed (`Restart_AfterStaleShutdownLatch_GenuineOutageStillSurfaces` guards this). A signal-driven stop reports `StopDueToProcessShutdown`, distinct from a token cancel's `StopDueToCancellation`; an explicit cancel wins when both are true, so a graceful `StopAsync` during a real SIGTERM still reports `StopDueToCancellation`.
- All tracing spans come from one `ActivitySource` named by the public const `SqlTableDependency<T>.ActivitySourceName` (`"SqlTableDependency"`). Consumers must `AddSource` it in their OpenTelemetry pipeline or every span is dropped (`StartActivity` returns null); exceptions still surface via `ILogger`/`OnException`, so "exception shows but no spans" means a missing `AddSource`. The name is a published contract — renaming is a breaking telemetry change; `ActivitySourceTest` guards it.
- Permissions: the library runs without database-wide `CONTROL`. The lever is **ownership, not grants** — the owner of a schema implicitly holds `CONTROL` (hence `REFERENCES`/`ALTER`/`RECEIVE`) on every object in it, with no `CONTROL` *row* in `sys.database_permissions`. So the Service Broker objects (queues + activation procedure) live in a fixed dedicated schema named by the public const `SqlTableDependency<T>.DefaultBrokerSchemaName` (`"SqlTableDependency"`) — there is intentionally NO public/configurable `brokerSchemaName` surface (kept the diff minimal). A single account just needs that schema created `AUTHORIZATION` it, no application code change. `SchemaName` still drives the trigger (it must live on the table). In `ScriptDropAll`, `{2}` = broker schema (drives `@schema_id` + queue/proc lookups) and `{5}` = table schema (the trigger `OBJECT_ID`/PRINT literals); the code-built `DISABLE/DROP TRIGGER` strings (`{3}`/`{4}`) also use the table schema. Getting `@schema_id` pointed at the broker schema while the trigger literals stay on the table schema is the subtle spot — `BrokerSchemaRoutingTest` asserts object placement and the `ControlPermissionTest` drop assertions cover teardown.
- `ConfigureAsync` calls `EnsureBrokerSchemaExistsAsync(DefaultBrokerSchemaName)` before the guard: if the schema is missing it runs `IF SCHEMA_ID IS NULL EXEC('CREATE SCHEMA ...')` (needs `CREATE SCHEMA`/`CONTROL`; owned by the connecting principal). It is race-safe — on `SqlException` it re-checks existence and only throws `BrokerSchemaUnavailableException` if still absent, so concurrent listeners and a missing `CREATE SCHEMA` right are distinguished. Pre-creating the schema (owner = app principal) means no `CREATE SCHEMA` grant is needed at runtime. `NamingPrefix` is derived from the table schema, so object names never depend on the broker schema (persisted reconnect still finds them by name). Note: database-scope `GRANT ALTER` is enough to `CREATE SCHEMA` (it is broader than `ALTER ANY SCHEMA`), so the `EnsureBrokerSchemaExistsAsync` failure-path test must use a CONNECT-only principal (`ConnectOnlyConnectionString`) — `NoControlConnectionString` holds db `ALTER` and would silently create the schema, masking the `BrokerSchemaUnavailableException`.
- The permission guard is `CheckUserHasPermissionsAsync` using `HAS_PERMS_BY_NAME` (in `SqlScripts.SelectEffectivePermissions`), NOT a name-scan. It reports the *effective* right however conferred (grant, role, ownership), so it accepts an owning-but-CONTROL-less principal and rejects one holding `CONTROL` only on an unrelated schema (which the old name-scan wrongly passed). Returns `1`/`0`/`NULL` (NULL = securable missing); treat anything but `1` as missing. It must run **after** `CheckTableExistsAsync` and after the ensure-schema step so the object/schema probes target real securables — otherwise a missing table/schema makes `HAS_PERMS_BY_NAME` return NULL and the guard masks `NotExistingTableException`. Required effective set: db `CONNECT` + `CREATE QUEUE/SERVICE/CONTRACT/MESSAGE TYPE/PROCEDURE`, `CONTROL` on the broker schema, `ALTER`+`SELECT` on the table. The broker schema is probed for `CONTROL`, NOT `ALTER`+`REFERENCES`: the listener does `WAITFOR ... RECEIVE` and the activation proc `RECEIVE`s, and `RECEIVE` on those queues is only covered by `CONTROL`/ownership — so a principal *granted* `ALTER`+`REFERENCES` directly (not owner) would have passed the old `ALTER`+`REFERENCES` probe yet failed at `StartAsync` with a `SqlException` (the `BrokerSchemaGrantsOnly` case in `ControlPermissionTest` guards this). Ownership confers effective `CONTROL` with no `CONTROL` row, so the owning-but-CONTROL-less principal still passes. db-scope `GRANT ALTER` does NOT confer `ALTER` on a schema or table — only ownership/`CONTROL`/object-level `ALTER` does. A `CONTROL ON SCHEMA::[dbo]`-only principal is rejected (it cannot write the dedicated schema). The old `SqlServerRequiredPermission` name-scan also demanded `EXECUTE`, `VIEW DEFINITION`, `VIEW DATABASE STATE` and `SUBSCRIBE QUERY NOTIFICATIONS`; the effective guard intentionally drops them — `SUBSCRIBE QUERY NOTIFICATIONS` is for `SqlDependency`/query-notifications (this library drives Service Broker directly and never uses it), and `EXECUTE`/`VIEW DEFINITION` on the activation procedure come implicitly from broker-schema ownership (the activation runs internally under `EXECUTE AS`, the app principal never `EXEC`s it). `ControlPermissionTest`'s `OwnsBroker` case proves the listen+drop lifecycle works without any of the four, so do NOT re-add them. Don't widen the trigger ownership-chain assumption either: the trigger is `WITH EXECUTE AS SELF`, so its body (which `SEND`s to the broker service in the dedicated schema) runs as the creating principal — a low-privilege user modifying the table needs no broker rights even though trigger and broker objects live in different schemas.
- `Telemetry.Log` (`Telemetry.cs`) writes every record **twice** — through `ILogger` and as an `ActivityEvent` on `Activity.Current` — so the span event must be gated on `logger.IsEnabled(level)` too. Without that gate `LogDebug` still reaches the telemetry backend whatever `Logging:LogLevel` says, because the `WAITFOR` span is started with a synthetic always-`Recorded` parent (`startIndependentTrace: true`) that nothing downstream can sample away. A null logger keeps the always-emit behaviour — there is then no configured level to honour (`LogToTelemetryTest` covers all three cases). It is deliberately a plain non-generic static and not a member of `SqlTableDependency<T>`: `SpinGuard` reports through the same pair, and hanging the writer off the generic would have forced an irrelevant `T` on it (and on its tests). This is not theoretical: a dev listener spinning on an empty `RECEIVE` wrote ~100k rows/day of `Executing WAITFOR command.`/`Starting to read.` into a shared App Insights and exhausted its daily cap for the whole estate, while `kubectl logs` showed nothing at all because the console correctly honoured `Default: Information`.
- The receive loop guards against its own spin, in `SpinGuard` (`SpinGuard.cs`; state on the instance, arithmetic in the statics so `SpinGuardTest` can assert it; the delay is an injected `Func<TimeSpan, CancellationToken, Task>` defaulting to `Task.Delay`, so the tests cover the whole ladder without waiting). A `WAITFOR (RECEIVE)` that comes back **empty** in under half its `TIMEOUT` is not waiting (`IsPrematureEmptyReceive`; half is generous because `StartAsync` floors the timeout at 60s and a healthy empty receive returns at the timeout — measured 120,004ms against `TIMEOUT 120000`). `ThrottleAsync` then logs at **Warning** — deliberately not Debug, so the fault is visible when the loop's own Debug lines are not — and backs off 1s doubling up to `BackoffMax`.
- Two things about that guard are easy to get wrong. **The cap must exceed `watchdogTimeout`** (it is `watchdogTimeout + 10s`, and `BackoffMax_ExceedsTheWatchdogTimeout` pins that): the receive command re-arms `BEGIN CONVERSATION TIMER` on every iteration and that statement *replaces* the pending timer, so while the loop spins fast the `DialogTimer` never fires, the stale dialog is never retired and the spin cannot clear itself. A capped iteration has to outlast the timer for the self-heal to happen at all — a flat 60s cap is below the *minimum* legal `watchdogTimeout` (`StartAsync` enforces `>= timeout + 60`, so `>= 120s`) and would silently keep the outage alive. **Only a data message resets the backoff** — not any row: a torn dialog can deliver an error or an ignored `schemas.microsoft.com/SQL/ServiceBroker/*` row on every iteration, so counting those as a genuine early return hands the spin a permanent bypass. `receivedDataMessage` is therefore set at `messagesBag.AddMessage`, past both the error and system-message branches.
- The spin warning fires while the backoff is still climbing and then once per 10 minutes (`ShouldWarn` + the `_sinceLastWarning` accumulator, which sums iteration times rather than reading a clock — nothing else runs during a spin, and it keeps the guard deterministic under test). Without the reminder the backoff stops changing at the cap and a 21h spin would warn only in its first few minutes, which is exactly the window an alert misses. The receive span is closed before the backoff, so a throttled iteration does not report its delay as WAITFOR duration — otherwise a spinning loop looks like a healthy long wait on the very dashboard used to spot it; closing it also closes the reader so the connection is not left mid-fetch through the delay. Observed cause of a real spin (Sep 2026): unexplained broker state after an ungraceful node reboot, which cleared ~21h later when the conversation timer fired and the dialog was re-established.

It also needs `Microsoft.VCRedist.2015+.x64`, or `SqlLocalDB.exe` fails silently with exit 53. Mixed mode is on by default; `xp_instance_regwrite LoginMode` fails on LocalDB and isn't needed.
- Docker on this box runs **Windows containers**, so the Testcontainers `DatabaseFixture` cannot start and, because it is an `[assembly: AssemblyFixture]`, *every* test in the project fails at initialisation — including pure unit tests that touch no database. `dotnet test` is therefore not a local signal here; the fallback is a scratchpad console project with `<AssemblyName>TableDependency.SqlClient.Test</AssemblyName>` (so `InternalsVisibleTo` still applies) referencing the library and asserting the internals directly. A better fallback for DB tests: LocalDB (`(localdb)\MSSQLLocalDB`, SQL 2025, mixed-mode, broker on) is installed — temporarily swap the container start in `DatabaseFixture.InitializeAsync` for an integrated-security LocalDB master connection string (drop `TableDependencyDB` first), run the filtered tests, then restore the fixture. Never commit that swap. LocalDB's broker catalog names (`sys.services`, `sys.service_contracts`, ...) are `Latin1_General_BIN` against a `SQL_Latin1_General_CP1_CI_AS` database, so concatenating or `UNION`ing them with `sys.objects` names needs `COLLATE DATABASE_DEFAULT` — the base `GetSurvivingDbObjectsAsync` helper hits this and fails there; use `AreAllDbObjectDisposedAsync` in new tests.
- DDL in `CreateDatabaseObjectsAsync` (message types, contract, queues, services, queue activation, `BEGIN DIALOG`, timer) is constant scripts in `SqlScripts` with every name bound as a parameter and `QUOTENAME`d into `sp_executesql` — identifiers cannot be parameters, and `ServiceAuthorization`/`QueueExecuteAs` are caller-supplied (`SqlInjectionTest` guards both). `QUOTENAME` returns NULL for input over 128 chars: never wrap it in `COALESCE(..., N'')` for an optional clause (that silently dropped `AUTHORIZATION`); use `CASE WHEN @x IS NULL` so the NULL reaches the `IF @sql IS NULL THROW` guard. The contract's message list travels as an `<m><m>name</m></m>` XML parameter because `STRING_SPLIT`/`OPENJSON` need compat level 130. The trigger and drop-all scripts still `string.Format` names in; they derive only from the existing table/schema names.
- The persisted receive batch looks the initiator handle up `WITH (NOLOCK)` and then arms `BEGIN CONVERSATION TIMER`; if the activation procedure ends that dialog in between, the arm raises 8426 (`conversation handle ... is not found`), which the batch's `TRY/CATCH` swallows. To test that race against the real batch (not a copy of its SQL), hold the dialog's lock in an open transaction (`BEGIN CONVERSATION TIMER` on it), wait until `sys.dm_exec_requests.blocking_session_id = @@SPID` shows the listener blocked, then `END CONVERSATION` and commit. 8426 is statement-level, so the batch still enters `WAITFOR` and the error only surfaces when it returns — wake it with an `INSERT` before asserting (`PersistedListener_SurvivesConversationClosedBetweenLookupAndTimerArm`).
- Self-healing (`CheckDatabaseObjectsAsync`, `AutoRepair`, `ReconnectTimeout`). Repair re-runs `CreateDatabaseObjectsAsync(repair: true)`; every step is idempotent, plus `EnableQueue`/`EnableTrigger`, because `CREATE OR ALTER TRIGGER` keeps a disabled trigger disabled. All repair, the loop's reconnect repair and the non-persisted final drop take `_repairLock`, and repair runs only while `_loopActive`. Without that, a heartbeat racing `StopAsync` would recreate what the drop just removed (`CheckDatabaseObjects_AfterStop_DoesNotResurrectObjects`). Non-persisted repair reuses a live dialog. When it must replace one, it ends the old one `WITH CLEANUP`: a plain end, or leaving it alive, would put `EndDialog`/`DialogTimer` on `_Sender` and fire the activation drop-all. The new handle is published only after commit, via a fresh `StrongBox<Guid>`, so the loop never reads a torn or rolled-back handle. Reconnect retries only a `SqlException` raised outside subscriber dispatch (`ReconnectPolicy`), not by connection state: a dropped receiver queue fails with the connection still `Open`. The outage ends only when a receive completes, and the drop-all `finally` sits outside the reconnect loop. Broker re-enable (`SqlScripts.EnableBroker`) is attempted only when `HAS_PERMS_BY_NAME(..., 'ALTER')` = 1. It runs `ENABLE_BROKER WITH NO_WAIT` from `master` via `EXEC`, so the issuing session doesn't count against the exclusive access it needs. It clears the library's own pool first and never uses `ROLLBACK IMMEDIATE`. The listener's own `WAITFOR` session also counts as "another user" to `NO_WAIT`, so a heartbeat can never enable the broker while the loop is connected. `TryEnableBrokerAsync` therefore first releases the receive connection: it cancels the per-connection `_receiveCts` (not the listener's token) and waits for `_receiveClosed`. The caller holds `_repairLock`, which keeps the loop from reopening until the enable is done. `NEW_BROKER` is chosen up front, by finding another database whose broker is enabled with the same `service_broker_guid`. Catching 9772 does not work: inside `EXEC`, `ERROR_NUMBER()` in the `CATCH` is the trailing 5069 ("ALTER DATABASE statement failed"). The reconnect loop reopens only after a health check that actually ran. Otherwise a database coming back between a failed check and the next open skips the repair, and a disabled broker never gets fixed, because `RECEIVE` still works locally without it. Objects are rebuilt even when the broker stays off, because DDL works without it. `BrokerSelfHealingTest` creates its own database: toggling the broker on the shared fixture DB needs exclusive access, and its admin connections must be `Pooling=false`, or an idle pooled session blocks the `NO_WAIT` enable. To force 9772, back up the database, restore it over itself `WITH REPLACE` (broker comes back off, same GUID), then restore the backup as a `_copy` `WITH MOVE ..., ENABLE_BROKER`. Disable the listener's login across the restore, or its reconnect can take the `SINGLE_USER` slot. Tests that assert the old immediate `StopDueToError` on a kill set `ReconnectTimeout = TimeSpan.Zero`. `SelfHealingTest` uses its own login so its `KILL`/`ALTER LOGIN DISABLE` cannot hit parallel tests.

## Git
- Agents never push commits, on any branch, by any route (`git push`, `git -C … push`, a GUI/MCP push tool, or a script that pushes). Commit locally and tell the user; the user pushes. `.claude/settings.json` enforces this with a deny rule and the `.claude/hooks/block-git-push.js` PreToolUse hook - do not remove or work around either.
